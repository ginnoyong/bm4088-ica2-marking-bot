# Static Reference: Table Relationships

All six scenario datasets use the same schema and relationships, listed below. The table names shown are base names — each scenario's actual dataset has `_set_1x` appended to every table name, where `x` is the scenario number (1–6). For example, in Scenario 1's dataset, `customers` appears as `customers_set_11`, `order_items` as `order_items_set_11`, and so on; in Scenario 3, `customers_set_13`, `order_items_set_13`, etc.

**Before matching any table reference in a formula against this list or against the data dictionary, strip the `_set_1x` suffix to get the base table name.** A reference like `customers_set_13[customer_age]` should be read as `customers[customer_age]` for the purposes of dependency resolution and relationship checking. Do not treat the suffixed name as a different or unknown table — it's the same base table, scoped to that scenario's dataset. If a table name doesn't match a base name once the suffix is stripped, only then treat it as unresolved.

| From | To | Cardinality | Cross-filter direction | Status |
|---|---|---|---|---|
| `customers[customer_id]` | `orders[customer_no]` | 1:1 | Double | Active |
| `orders[order_id]` | `order_items[order_no]` | 1:many | Single | Active |
| `products[product_id]` | `order_items[product_no]` | 1:many | Single | Active |
| `sellers[seller_id]` | `order_items[seller_no]` | 1:many | Single | Active |

**Leniency on the `customers`↔`orders` cardinality description.** The confirmed, true behaviour is 1:1/Double, per the row above and the reasoning in the notes below — that's what actually governs whether a formula relying on this relationship works, and the DAX module's own correctness checking still uses it as ground truth, unchanged. Separately, if a marker or a student's report describes or assumes this relationship as 1:many, Single instead, don't correct or flag that as an error. It's an easy point to get wrong — "customer to orders" reads as 1:many on the surface, and only a careful read of `customer_id`'s actual definition in the data dictionary reveals it's really per-session, not per-customer — so treat either description as an acceptable framing when it's the description itself under discussion. This leniency is narrowly about the label; it does not extend to the `customer_id`/`customer_unique_id` distinction below, which remains a real, fully-enforced error class regardless of how the relationship is labelled — a formula miscounting unique customers via `customer_id` is wrong for a reason that has nothing to do with what the join is called.

## Notes

- The `customers`↔`orders` relationship is the only bidirectional one — filters can flow both ways between these two tables. All other relationships are single-direction, flowing from the "one" side to the "many" side (`orders`, `products`, `sellers` → `order_items`) as expected in a star schema. `order_items` is effectively the fact table.
- Because `customers`↔`orders` is already bidirectional, a formula that relies on filtering `customers` from a filter on `orders` (or vice versa) is expected to work and does not need to be flagged for marker verification — that's the one relationship where bidirectional behaviour is confirmed, not assumed.
- A formula that relies on bidirectional propagation between any of `orders`, `products`, or `sellers` and `order_items` (i.e. filtering the "one" side from a filter applied on `order_items` alone, without an explicit `CALCULATE`/`ALL` override) should still be flagged for marker verification, since those relationships are single-direction per this reference.
- **`customers[customer_id]` is not a unique-customer identifier — it identifies a customer-session/order, and this is why the relationship to `orders` is 1:1.** The field that identifies a genuinely unique customer is `customers[customer_unique_id]`. This is a common error surface: watch for any formula that uses `customer_id` (via `DISTINCTCOUNT`, `COUNTROWS(VALUES(...))`, grouping, or similar) where the report's stated purpose is to count or group by unique customers — e.g. "number of unique customers," "average orders per customer," "customer segments." That formula will actually be counting/grouping by session/order, not by customer, and should be flagged as a mismatch even if the DAX syntax is otherwise correct and the relationship traversal is fine. Only `customer_unique_id` supports a genuine per-customer claim.
- This distinction isn't called out separately anywhere in the source material — it has to be read out of the data dictionary's own column descriptions (see `data_dictionary.md`). General principle for the DAX module: when resolving a column reference, don't just confirm the column exists — read its description and check that the report's stated purpose for using it actually matches what the description says the column represents, particularly for any field whose name alone implies uniqueness, identity, or a specific grain (e.g. anything named `_id`, `_no`, `_code`, or similar). A column existing with a plausible-sounding name is not the same as it meaning what the report assumes it means — the `customer_id` case above is the known example, not the only possible one.
